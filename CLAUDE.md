## User Flow

`ENTRY → VERIFICATION → INVITATION`. Не обязаны быть отдельными URL/роутами — прототип реализует всё как единый компонент с внутренним state (`screen: 'select' | 'invite'` + модалка verification поверх select-экрана) и fade/overlay-переходами между состояниями. Это рабочий паттерн, следуй ему, если нет причины делать иначе.

- **ENTRY**: атмосферный фон (`tower-dragons.webp`) + единая иллюстрация дерева (`entry-tree.webp`) с 39 кликабельными яблоками — имя гостя под каждым яблоком, тап открывает VERIFICATION для этого гостя. Не список/grid и не поиск — реализовано как дерево (см. `EntryScreen.tsx`, коммиты #10/#11). Дерево не показывается сразу: пока скролл не перешёл границу (верх дерева поднимается в верхнюю треть viewport, `useScrollGate("0px 0px -70% 0px")`), иллюстрация скрыта сплошной заливкой seam-тона башни (`.treeVeil`) и сама картинка держится в `opacity: 0`; после порога заливка и картинка плавно меняются местами, следом загораются яблоки. Порог двусторонний: при обратном скролле наверх дерево снова затемняется заливкой (`useScrollGate` — в отличие от one-shot `useScrollReveal`). Пока дерево закрыто, его контейнер `inert` — яблоки не фокусируются и не кликаются.
- **VERIFICATION**: модальное окно поверх ENTRY (не отдельный экран) — вопрос гостя, input, submit, кнопка возврата. Неограниченное число попыток, мягкая ошибка без формулировок "заблокировано".
- **INVITATION**: единый vertical scroll — Hero → Date/Time/Place (включает CTA «Построить маршрут» и иллюстрацию карты) → Dress code → Gifts → Finale (ромб, инициалы пары, дата). Дерева имён в INVITATION нет — дерево используется только на ENTRY. Доступ сохраняется минимум в рамках browser session (`sessionStorage`/in-memory).

## Architecture (зафиксировано)

Стек выбран осознанно и является ограничением, а не рекомендацией по умолчанию — не меняй без явной просьбы.

- **Next.js + TypeScript + App Router, static export (`output: 'export'`).** Причина: деплой — ручная заливка статических файлов в S3 (без Lambda/сервера/edge functions), поэтому любой server-side рантайм (Route Handlers, Server Actions, middleware, ISR, on-demand image optimization) на проде недоступен и использоваться не должен. `next build` производит статическую директорию (`out/`), которая целиком заливается в S3.
- **Styling:** CSS Modules + централизованные design tokens (CSS custom properties). Без Tailwind и без UI-кит библиотек (Material UI/Ant Design и т.п.) — вся визуальная система custom.
- **Verification:** **клиентская** (см. подробный trade-off в разделе Verification & Privacy) — сервера для проверки ответа нет и не будет.
- **Animations:** CSS keyframes/transitions + `IntersectionObserver` для scroll-reveal в первую очередь. GSAP/Framer Motion подключать только если CSS реально не хватает для нужного качества — не устанавливать заранее.
- **Images:** `next/image` с `images.unoptimized: true` (обязательно для static export — на S3 нет сервера оптимизации изображений). Ассеты предварительно оптимизировать (resize/WebP/AVIF) до попадания в `public/`; `next/image` всё равно даёт lazy-loading, explicit dimensions (без layout shift) и `sizes`, даже без runtime-ресайза.
- **Deployment:** инфраструктура развёрнута через Terraform (`terraform/`, Yandex Cloud) и **применена** — не гипотетическая. Object Storage bucket на домене `sacred-castle-wedding.ru` со static website hosting (index/error document — `index.html`, т.к. приложение однострочное); собственная DNS-зона с apex ANAME на bucket-эндпоинт (домен делегирован на её NS-записи у регистратора); управляемый TLS-сертификат (Yandex Certificate Manager, DNS_CNAME challenge) подключён напрямую к bucket — **без CDN/CloudFront-аналога**, это осознанное решение, а не временное упрощение. Terraform state — в отдельном S3-совместимом бакете (`state_backend.tf`), без нативного locking (избегать параллельных `apply`). Доступ к bucket — через сервисный аккаунт со статическим ключом (`storage_sa.tf`, S3 API не принимает IAM-токены). Деплой самого контента — `next build` → `scripts/deploy.sh` (или `make deploy`/`make release`): раздельная синхронизация `_next/static/**` (immutable, долгий кэш) и всего остального (`must-revalidate`), с `--delete`. Подробности разовой настройки кредов — в `README.md`.

Прототип (`Wedding Invitation.dc.html`) — источник поведения и композиции, но **не источник кода**: его шаблонизатор (`sc-if`/`sc-for`/`DCLogic`) специфичен для инструмента прототипирования и не переносится напрямую в React/Next.js компоненты. Переноси логику и анимационные тайминги осмысленно, а не копированием разметки.

### Что взять из прототипа концептуально

- State machine `select → verify(modal) → invite`, fade/overlay-переход между состояниями (~550ms setState-последовательность с overlay opacity 0→1→0).
- Scroll-reveal: секции появляются (`opacity 0→1`, `translateY(28px→0)`) при пересечении viewport; при `prefers-reduced-motion` — сразу все видимы, без слушателя скролла.
- Дерево (ENTRY): яблоки появляются с последовательной задержкой (`transitionDelay = index * 0.22s`), небольшой scale-in.
- Туман/луна: медленный `translate`-дрейф на `radial-gradient`, `moonGlow` пульсация — оба отключаются через `@media (prefers-reduced-motion: reduce)`.
- Приветствие зависит от пола гостя (`Дорогой`/`Дорогая`) — модель гостя должна нести это поле (или прямой текст приветствия).

### Что НЕ переносить как есть

- **Единый общий ответ на всех гостей.** В прототипе `CORRECT_ANSWER = 'москва'` — один ответ для всех, это упрощение для демонстрации. По ТЗ (раздел 6) каждый гость должен иметь собственные допустимые ответы — обязательно реализовать per-guest модель (`acceptedAnswerHashes[]`, см. Data Model / Verification & Privacy), не хардкодить общий ответ.
- Инлайновые style-объекты и кастомный `DCLogic`/class-component API — заменить на идиоматичные React-компоненты. Т.к. verification и часть анимаций выполняются на клиенте (static export без сервера), большинство интерактивных секций будут Client Components (`'use client'`); Server Components уместны только там, где не нужен рантайм-JS (чисто статичная разметка секций).

## Data Model

Централизованная модель гостя (форма из ТЗ, адаптировать по необходимости, но не размазывать данные по компонентам):

Фактическая реализация (`src/types/guest.ts`) выбрала вариант с `gender`, а не произвольным текстом greeting:

```
Guest {
  id: string
  displayName: string
  gender: "m" | "f"                // → greetingForGender() даёт "Дорогой"/"Дорогая", см. src/data/event.ts

  acceptedAnswerHashes: string[]   // SHA-256(normalizeAnswer(answer)), не plaintext
```

Guest data и event content (дата, площадка, dress code, gifts copy) — в отдельном `data/`-слое, не в JSX. Все незаполненные значения (время сбора, текст dress code, финальные пожелания и т.д.) держать как явные `TODO`/placeholder-константы, легко находимые grep'ом.

## Verification & Privacy

Это **не** реальная security-граница — персональный вопрос это атмосферный элемент и лёгкая проверка "свой/чужой", а не аутентификация. Это принципиально не меняется решением ниже.

### Trade-off: static export на S3 → верификация на клиенте

Исходно ТЗ предпочитает server-side verification, чтобы `acceptedAnswers` не попадали в клиентский бандл. Но целевой деплой — ручная заливка статики в S3 без какого-либо серверного рантайма, поэтому Route Handler/Server Action недоступны на проде (Next.js `output: 'export'` их не поддерживает в рантайме). Значит проверка ответа неизбежно выполняется в браузере.

Зафиксированное решение — не хранить сами ответы в bundle в открытом виде, а хранить их хэш:

- Ответ гостя приводится через `normalizeAnswer()` (см. ниже), затем хэшируется через `crypto.subtle.digest('SHA-256', ...)` (Web Crypto API, встроен в браузер — без доп. зависимостей).
- В `data/guests` хранятся **hex-хэши** допустимых ответов (`acceptedAnswerHashes[]`), а не сам текст ответа.
- При submit: нормализовать ввод пользователя → посчитать SHA-256 → сравнить с массивом хэшей гостя.
- Это **не криптостойкая защита** (короткие бытовые ответы перебираемы), а разумное снижение тривиальности — ответ не читается напрямую из view-source/devtools/Network. Этого достаточно для заявленной модели "свой/чужой", не для настоящей authentication.
- Т.к. авторы контента (заказчик) будут присылать ответы обычным текстом, нужен небольшой build-time/dev-time скрипт-конвертер (например `scripts/hash-answers.ts`), который берёт файл с plaintext-ответами и генерирует `data/guests`-файл с хэшами. Сам plaintext-источник в репозиторий/бандл не должен попадать в финальном виде (или должен явно исключаться из клиентского импорта).

Остальные правила без изменений:

- Нормализация ответа — одна централизованная функция (`normalizeAnswer`): `trim` + `toLowerCase` + схлопывание повторяющихся пробелов. Без fuzzy matching. Применяется одинаково и при генерации хэшей, и при проверке ввода.
- Несколько допустимых ответов на одного гостя — несколько хэшей в `acceptedAnswerHashes[]`.
- Никаких доп. персональных данных не собирать. Аналитику/трекинг не подключать без отдельного запроса.

## Animation Rules

Допустимо: лёгкое появление/парение драконов, дым, subtle parallax в hero; медленный многослойный туман; fade/slide + последовательное появление секций при скролле; последовательное появление яблок дерева + reaction на hover/tap; спокойные fade/fog переходы между ENTRY/VERIFICATION/INVITATION.

Запрещено: bouncing-анимации, distracting particles, резкий zoom, эффекты мешающие чтению. Не мотион ради мотиона.

**`prefers-reduced-motion` обязателен** (acceptance requirement, не nice-to-have): при reduced motion — отключать/резко сокращать parallax и бесконечный decorative motion (туман, луна), минимизировать transition distance, интерфейс должен оставаться полностью функциональным. Прототип уже даёт рабочий паттерн: при reduced motion все scroll-reveal секции считаются сразу видимыми, а не ждут скролла.

## Accessibility

Достаточный контраст; читаемые размеры текста и tap targets; семантический HTML; keyboard navigation для интерактивных элементов; видимый focus state; `label` для input; `alt` для смысловых изображений; декоративные слои (туман, драконы-фон, свечение) скрыты от accessibility tree (`aria-hidden`); функциональность не должна зависеть от hover (основной путь — тач/клик/клавиатура).

## Performance

- `assets/tower-dragons.png` (1.9MB PNG) нужно оптимизировать/конвертировать (WebP/AVIF, responsive sizes) перед продакшен-использованием — не грузить как есть.
- Lazy-load below-the-fold иллюстрации (маршрут, подарки); hero не lazy-load.
- Минимизировать JS, не тянуть тяжёлые анимационные библиотеки без необходимости.
- Избегать layout shift (заданные aspect-ratio для арт-блоков — паттерн уже есть в прототипе через `aspect-ratio` на placeholder-блоках).
- Учитывать медленный мобильный интернет — первый экран не должен требовать десятков мегабайт.

## Testing

Framework для тестов ещё не выбран (нет package.json). Когда стек появится, минимальный объём:

- **Unit:** `normalizeAnswer()`, хэширование и сравнение по `acceptedAnswerHashes[]`, скрипт-конвертер plaintext→hash.
- **Component/integration:** выбор гостя, верный/неверный ответ, возврат к списку, сохранение unlock в session, ветка reduced-motion (если тестируемо).

Не гнаться за покрытием декоративных деталей (туман, парение драконов и т.п.).

## Coding Conventions

- Mobile-first, accessibility by default, respect reduced motion — не опционально.
- TypeScript strict mode, без `any` без необходимости.
- Данные гостей/контента — отдельно от presentation-компонентов, никогда не хардкодить guest-specific данные внутри UI.
- Сервера нет — все данные (включая `acceptedAnswerHashes`) неизбежно в client bundle. Именно поэтому ответы храним только как SHA-256 хэши, никогда как plaintext (см. Verification & Privacy).
- Минимизировать зависимости; не ставить новую библиотеку, если задача решается существующим стеком.
- Не создавать дублирующую архитектуру рядом с уже выбранной; не менять художественное направление без явной просьбы.
- Избегать преждевременной абстракции — три похожие секции лучше, чем ранний generic-компонент.

## Definition of Done

После любого изменения:

- Прогнать релевантные lint/typecheck/tests/build (когда tooling появится).
- Вручную проверить основной user flow: ENTRY → выбор гостя → верный/неверный ответ → INVITATION.
- Проверить mobile layout (320–430px), включая portrait/landscape, safe areas, отсутствие overflow/layout shift.
- Проверить desktop (Chrome/Safari/Firefox/Edge) — учитывая, что baseline-layout это центрированная "карточка" ограниченной ширины.
- Проверить browser console на ошибки.
- Проверить `prefers-reduced-motion` ветку отдельно от нормального motion.
- Убедиться, что анимация никогда не является условием доступа к контенту.
- Проверить focus state для интерактивных элементов.
- В конце — перечислить, что изменено и что осталось нерешённым/открытым.

Для UI-задач не считать готовым только потому, что JSX скомпилировался — нужна визуальная проверка (иерархия, spacing, overflow, focus, reduced motion).

## Git Workflow

- **Открытие PR — не финальный шаг задачи, а начало приёмки.** Мёрж PR не автоматический и не считается завершением работы сам по себе — требуется явное подтверждение пользователя перед `squash and merge`, независимо от статуса CI.
- **Приёмка для кода/UI — визуальная.** Перед открытием PR: **агент сам** поднимает dev-сервер (`npm run dev`, фоном) и сообщает пользователю адрес/порт — не просить пользователя запускать сервер самостоятельно. Пользователь смотрит результат визуально в браузере и подтверждает, что всё работает. Только после этого подтверждения — открыть PR и сразу выполнить `squash and merge`.
- **Приёмка для изменений Terraform/инфраструктуры — по плану.** Сначала описать пользователю планируемые изменения (например вывод `terraform plan`), не применять их. Только после подтверждения пользователем — применить (`terraform apply`), затем открыть PR и сразу выполнить `squash and merge`.
- Не выполнять `squash and merge` без явного подтверждения пользователя ни в одном из этих сценариев.
- После `squash and merge` ветку удалять не нужно.

- Общий или персональный greeting-текст для каждого гостя (сейчас реализован только общий вариант по полу — см. Data Model).
- Только русский язык или RU+EN.
- Происхождение финальных иллюстраций карты усадьбы и конверта (арт заказчика, иллюстратор, доработанный AI-арт) — они всё ещё текстовые заглушки (`PlaceholderIllustration`). Hero (башня+драконы) и иллюстрация ENTRY-дерева — уже готовый production-арт, не открытый вопрос.
- Visual references сверх уже описанной эстетики.
- Допустимо ли показывать список всех имён до verification (текущий прототип — да, ENTRY показывает весь список сразу).
- Сохранять ли unlock между визитами (сейчас — только в рамках session, per ТЗ).
- Финальные шрифты — подтвердить Cinzel/Cormorant Garamond/EB Garamond или заменить.
- Нужны ли social sharing preview / PWA-подобные ассеты.
